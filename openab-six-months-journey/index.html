一開始只是看了社群的影片，跟著裝 openclaw 來玩。後來換成 OpenAB，玩到想把它推給同事，還真的架了一套網頁後台；結果折騰了半年，現在每天最常開的，反而是為了讓自己能在手機上接回終端機，順手做出來的工具。

引言
#

回頭看這半年多折騰 OpenAB 的過程，其實蠻有趣的。原本只是想弄懂這東西怎麼跑，後來發現人在外面也能透過 Discord 叫 agent 幫忙查問題，就開始想：這麼好用的東西，做個介面給同事用應該也行吧？我那時候還真的想得蠻遠，連怎麼讓大家填表單就生出專屬 bot 都規劃好了。

這段時間做的幾樣東西，有些已經另外寫成筆記了，像是建立自己的機器人、讓 agent 會畫圖、部署到 AWS ECS，還有拿起手機就能工作。這篇不打算重講操作步驟，比較想記錄這一路的轉折：為什麼當初會想做那套後台、中間踩了哪些坑、推廣為什麼失敗，以及最後怎麼慢慢收斂成現在自己這套 agent 工作環境。

從 OpenClaw 玩到 OpenAB
#

最早會接觸到這個生態系，是因為當時在社群看到的教學影片，在介紹「怎麼安裝 openclaw」。那時候我對這種東西幾乎啥都不懂，純粹覺得酷，就跟著影片一步一步照做。老實說，做出來的當下很開心，雖然其實根本不知道要拿它來幹嘛 XD。

過了一陣子，社群突然沒那麼常聊「龍蝦」了（OpenClaw 的 logo 是一隻紅色龍蝦，中國網友常戲稱部署使用它叫「養龍蝦」），大家改口開始聊 OpenAB。我點進去看了看，那時候幾乎找不到什麼入門文章，GitHub 上的文件也看不太懂，想說算了，先放著吧。

直到某天比較有空，才靜下心來認真啃 GitHub 文件。一開始我是從 Windows 的 .exe 版本開始玩，跑起來之後覺得很有意思，就逐步升級，乾脆買了一台 mini PC 專門拿來裝 k3s。

買 mini PC 配 k3s 這件事，說穿了就是一筆學習投資，我當時手上其實根本沒幾個 agent 要跑。純粹是剛接觸對這套技術蠻有興趣，加上 OpenAB 本身以安全優先設計、k3s 又是比較正規的部署方式，我就想說與其在 Windows 上踩一堆環境相容性的雷，不如直接弄一台原生環境，把這套部署好好摸熟。（裝機過程後來也整理成新手入門篇了。）

用了一陣子，真正讓我覺得回不去的關鍵轉變，是它把我的生產力從座位前面解綁了。

以前要寫點東西、跑個指令或查個問題，非得坐到電腦前面不可，人在外面就只能先記著；接上 Discord 之後，隨時拿起手機在頻道裡講幾句話，事情就能在背景開始跑，等我有空再回來看結果就好。至於為什麼選 Discord，原因也很現實：官方最推薦、支援度最高。其他平台不是部分功能沒實作，就是沒什麼人維護，除非自己 fork 下來改完發 PR，不然用 Discord 還是最省事。

當然，剛開始用也沒有那麼順利，踩最多的坑其實是 steering 跟 AI 的基本功——這跟 OpenAB 本身沒什麼關係，比較像是我們自己得學會怎麼讓 LLM 區分上下文、搞清楚各家模型能力標準不一的脾氣、怎麼讓 AI 乖乖讀指引文件，還有怎麼寫 skill 跟用 skill。

我初期拿它來做的事情很單純，就是聊天。印象超深刻的是，我那時候很認真設定了好幾個 agent 的背景故事、人物性格，想說來玩點角色扮演，結果每家 LLM 在 Discord 裡都超容易出戲，聊到一半會突然一本正經地回我：「我先看看文件再決定怎麼回覆。」整個氣氛瞬間冷掉。不過在當時的測試裡，kiro 在這方面算是表現得最好的。

真正的轉折是後來拿它處理開發跟維運任務，發現對線上 troubleshooting 特別有奇效。碰到不熟的環境，新手常常光是想第一步要查哪裡就卡住了，這時候先在 Discord 跟 agent 描述狀況，至少很快能抓出幾條線索往下查。看到這個效果不錯，我就開始想，那乾脆引導同事也一起來用吧。

我做了一套後台給同事用
#

當時想在公司推廣的動機其實很單純：一方面覺得這東西真的好用，想分享出來幫大家節省時間；但老實說也有私心，想把盤子做大，越多人用影響力就越大，在這個生態系裡面的人自然也能拿到更多好處。

同事為什麼推不動？
#

但實際推起來才發現，同事那邊卡了兩層很現實的問題：

  1. 想像力還沒被打開：大家還是習慣傳統的工作思維。明明這件事已經可以直接指派給 AI 去跑了，很多人還是習慣像以前寫程式一樣，自己鑽進細節裡慢慢查、自己拼湊。
  2. 技術門檻高，加上文件稀少：OpenAB 這種偏極客的工具，光用嘴巴講有多厲害是沒用的，一定要把畫面秀出來、讓別人看到「原來可以這樣用」，他們才會有興趣試。就算看得懂文件的人，初期也很難自己想出新玩法；沒什麼強烈動機的話，大家很快就會轉向比較輕鬆的本地端 CLI，反正都在自己電腦上跑就好，根本不需要特別透過 Discord 繞一圈。

後台做著做著就變大了
#

既然大家覺得門檻高、CLI 太硬派，那我就幫大家做一個網頁管理介面總行了吧？

那時候我的規劃其實蠻宏大的，整個架構拆成三塊：共用核心專案 k3s-ops，搭配對應的 *-oab-bots 跟 *-oab-web——這樣拆是想說未來如果開放出去，其他人也可以在自己的環境依需求架一套出來。至於公司這邊，其實是我架好做給大家用的，並不是要同事各自去建；網站管理介面本身有做帳號機制，他們登入就能直接用我開發好、串接好的功能，像是查案件、看資料、點按鈕就直接跑審查，全部都是開箱即用的。家用端這邊我則先做了 nuc-k3s-bots 和 nuc-k3s-web 來試水溫，後來幾次整併，網頁最後收進 oab-k3s-bots/web/，家用的部分現在是由 art-bots 承接。

不過老實說，這套網頁介面的很多程式細節，一開始連我自己都不知道。因為當時幾乎是全權交給 AI 去寫、我只看最後跑出來的結果，所以問題很多、修了很多次。後來為了能掌握細節、更好地去調整它，我反而花了很多時間在補技術債跟知識債——不斷反過來問 AI：這段是怎麼做出來的？整體架構是怎樣？邏輯是什麼？這樣寫真的可以嗎？有沒有不合理的地方？為什麼要這樣做而不是那樣做？這些問句佔據了我非常多時間，修修補補到最後累了，才慢慢沒再深入去追。

技術棧大概是這樣：oab-k3s-web 用 Python FastAPI 當後端，前端是 Jinja 配原生 JS，資料庫用 SQLite，整包部署在 K3s 上面。整個資料流跑起來像這樣：

網頁 (Web Pod) -> host ingress 目錄 -> host worker (k3s-ops-worker) -> local k3s -> Discord

Web Pod 平常只讀整理過的資料快照跟 K3s 唯讀資訊，要改設定不會直接動系統，而是寫進主機上的私有 ingress 目錄，等 systemd timer 觸發 k3s-ops-worker 去執行，做完再把結果存回 SQLite。其實後來也有聽說官方有 openab gateway 可以直接跟 OpenAB pod 溝通，但我當時因為還有管理一堆 bot 的需求，就硬生生繞了 worker + k3s 這一大圈。

本來只是想在網頁上查案件、跑審查，後來越塞越多：bot 狀態管理（部署、重啟、scale、換 Discord token）、技能、記憶、權限控管（RBAC）、流量監控、設計文件、簡易開發看板全都放進去了。我甚至還想順便做個 CLI 來控制 agent，最好後台跟 CLI 都能共用同一套核心。現在回頭看，每個想法單獨拿出來都講得通，全部塞在一起做真的沒必要。

我一開始是真的這樣天真的認為
#

除了我自己原本就在用的案件審查工作流（網站透過 API 拉案件清單 → 右鍵填表單選 review 方式 → 資訊帶給 Discord 的 main agent → 分派各面向 reviewer agent → 統整摘要讓我確認後回覆），當時最花心思設想的其實是「BOT 自動化建立」。

那時候公司裡真正有在接觸 AI 的人不多，手動建一個 Discord bot 對我來說也還蠻花時間。我就想，如果 PM 或業務單位有需要，只要在網站上填個表單、放上他們自己的 context knowledge base，系統就能自動生出一個專屬的 online Discord agent——畢竟差異只在資料嘛！我一開始是真的這樣天真的認為，把這段手動的工省下來，大家就會想拿去用。

推廣結果與後來想通的事
#

老實說，推廣的成效就是失敗了。同事有稍微試用幾次，後來就很少開了。

一方面公司文化本來就不太重視這種「沒有實際訂單收入」的內部工具；另一方面，那段時間剛好遇到業務量變少、人來來去去、組織動盪改革，表面上「嘴巴支持、行動無」，實際上大家人心惶惶，擔心自己的工作保不保得住，哪還有心思去學新工具。後來一堆人離職，AI 的出現也讓老闆覺得可以進一步精簡人力，那些原本設想給 PM 跟業務用的專屬 bot，自然也就不再需要了。

冷靜下來想，這次失敗背後其實還有兩個更深層的原因：

第一，我當時還是用傳統「集中式後台」的思維在做東西。大家摸熟了本地 AI 之後，慢慢會形成自己的工作流，有需要也會自己建 bot，根本沒什麼動機去點你網頁上寫死的固定按鈕。「填表單生 bot」這件事的價值，只成立在「建 bot 很難」的那短短幾個月裡，很快就被時代超越了。

第二，AI 進步實在太快了。以前覺得很棒的設計其實很快就過時，保鮮期沒有我想的那麼久。連我自己過幾個月回頭看，當初費心設計的那些 bot 設定，也有好幾個已經不太需要了；熱情一退，動機自然也就沒那麼強烈。

不是砍掉，而是停止
#

後來我對這套後台的態度不是砍掉重練，而是停止。已經做好的功能都沒刪，只是停止推廣、停止開發新功能，只留著日常還在跑的流程偶爾微調。

目前公司那邊還是有在用，但也僅限於已經接進日常工作的部分，後續不再考慮擴充。繞了這麼一大圈我才發現，反而是像 art-term 這種我自己每天真的在用的東西，我才比較有在持續關注。

回到指令列：openab-pty 與 art-term
#

從 ACP 到 openab-pty
#

OpenAB 本身是透過 ACP（Agent Client Protocol）跟 Codex、Kiro 這類 coding CLI 溝通。從 Discord 送進來的訊息會先經過 OpenAB，再交給後面的 CLI：

Discord -> OpenAB -> coding CLI（透過 ACP）

不過各家 CLI 對 ACP 的支援度不太一樣，有的原生就支援，有的還得靠開源社群的橋接專案（像 codex-acp）才接得起來。

這套模式用久了，我開始感覺到一個落差。長期用 coding CLI 的人，很習慣終端機裡那種訊息跟狀態一目了然的感覺；但透過 ACP 接到 Discord 之後，中間資訊會被過濾掉不少。這也不能怪 OpenAB，畢竟通訊平台面對的不只是工程師，還有業務或行政人員，隱藏部分繁瑣的工具調用對一般人來說確實比較友善，但對想看完整執行狀態、甚至想中途接手的我來說，總覺得隔了一層紗。

這也是後來我把 openab-pty 加進來的契機。不過要先說，ACP 跟 pty 並不是互斥的，而是互補：openab（走 ACP）是你出嘴叫 agent 做事，適合遠端交辦；openab-pty 則是讓你直接連進去自己打字，適合想親自看檔案、下指令或排查問題的時候。

簡單講一下 openab-pty 的做法：它是一個遠端沙箱終端機的 runtime，會在鎖定的容器裡開一個 shell（UID 1000、沒有 sudo、根檔案系統唯讀，工作區是暫時的），連線走 tailnet 加上每個 session 獨立的 token，終端機的輸入跟輸出再透過 WebSocket 傳送。

因為沒有 Mac，所以我自己造了一個輪子
#

差不多同個時期，pahud 針對 macOS 跟 iPad 推出了 OpenAB Connect 和 OpenAB Remote，直接把 openab-pty 跟桌面操控整合在一起。我看著其實蠻心動的，偏偏它只支援 Apple 生態系，我平常主力是 Windows 跟 Android，完全用不到。

講起來也有點好笑，我那時候手上其實只是想做一個簡單的手機小說閱讀器——因為看小說一直要等廣告，我受不了。偏偏想到要加什麼功能、改什麼介面，往往就是手機拿在手上看小說的時候，還要等回電腦前面才好處理就很煩。要是能直接從手機連回終端機，想到什麼就用語音跟家裡的 agent 許願，好像會方便很多。既然官方沒出 Windows / Android 版，那就自己做一個吧，這就是 art-term 誕生的動機。

技術架構上，art-term 就是 openab-pty 的連線客戶端，大概長這樣：

Windows/Android UI 或 Ubuntu TUI
        │
        ▼
  art-term-core (共用 Rust 核心)
        │
        ├── HTTPS/WSS ──> openab-pty Runtime ──> tmux Shell ──> coding CLI
        │
        └── MCP ────────> instance-mcp (直接拿桌面截圖預覽)

我把連線、認證、歷史紀錄、MCP 截圖這些共用邏輯全部抽進 art-term-core，介面再分兩邊做：Windows 跟 Android 用 Tauri 2 + Vue 3 + xterm.js（共用 apps/client）；Ubuntu 則是用 Ratatui 寫了 TUI 版本（art-term binary），還支援 Sixel 圖片預覽。平台間要分開處理的，就只剩鍵盤、觸控跟憑證儲存。

講到命名跟技術選型其實也蠻隨性的。一開始純粹自己用，專案就叫 my-cli，後來想說好像可以公開給大家參考，才改成 art-term（art + terminal）。至於為什麼選 Tauri + Rust + Vue 這麼潮的組合？老實說那是問 AI 建議的——我當時只提了一個需求：「我要核心共用、UI 分開處理」，AI 推薦什麼我就直接用什麼了 XD。

實際在手機上怎麼操作，我另外記在OpenAB 新手入門：拿起手機就能工作那篇，這邊就不重複了。

另外留一台電腦給 agent 用：openab-computer
#

把遠端終端機搞定之後，下一個問題很快就來了：現在的 agent 已經有能力看畫面、操作瀏覽器了，但你敢把平常主力電腦上的瀏覽器直接交給它嗎？

我是不敢啦。主力電腦裡有太多機敏資料、各種網站的登入 cookie 跟公司帳號，如果哪天 agent 逛到一個藏了惡意指示的網頁（prompt injection），回頭剛好又能用到那些已登入的帳號，那真的是出大事。

另外還有一個很實際的背景：像 muse ai 或 grok bot 這類工具現在都能幫人訂票、比價、下單，動作快的網站已經開始在封鎖雲端機房的 IP 了。如果是用自己家裡的網路 IP 去開瀏覽器，在對方網站看起來就跟家裡的人正常上網一樣，比較不容易被擋。

所以我的做法很單純：另外找一台乾淨的小電腦或樹莓派，裡面不放任何個人隱私資料，瀏覽器也不登入自己的帳號，純粹提供瀏覽器跟桌面環境給 agent 調用。

把官方的 OpenAB Computer 接進來
#

這時候就剛好用到 OpenAB 官方提供的現成工具：openab-computer（原本叫 instance-mcp，MIT 授權）。只要把它裝在同一個 tailnet 裡的另一台機器上（Mac、Linux 小主機或樹莓派都可以），就能透過 MCP（Model Context Protocol）把那台機器的桌面與瀏覽器能力暴露給 agent。你可以把 MCP 想像成 agent 世界的 USB-C，讓 agent 用統一規格呼叫外部工具，不用每接一個就重寫一套 API。

從它的權限設計就能看出為什麼要獨立一台機器：observe 只能看系統資訊跟截圖（sys_info、screenshot）；owner 則開放完整工具，除了動滑鼠、鍵盤、操作瀏覽器，還包含以登入使用者身分執行 shell 指令（exec）。驗證走 bearer token 加上 Tailscale 身分檢查，如果目標機器只能主動往外連（dial-out），它也支援 switchboard 模式（reverse attach）。

這套工具接進來之後，剛好跟我前面做的 art-term 串在一起。因為 art-term 本來就是受到 OpenAB Connect 跟 OpenAB Remote 的影響才做出來的，我也順勢在 art-term 裡加了桌面預覽，直接用 MCP 拿截圖，畫面不用再繞回 PTY。

前面架構圖寫的 instance-mcp 是舊名。產品正式名稱叫 OpenAB Computer，從 v0.12.0 起執行檔等技術名稱才從 oab-instance-mcp 換成 oab-computer（升級說明）。

理想很豐滿，但目前用得很克制
#

接的時候我當然也想過，以後是不是連訂票、代購、登入帳號下單都可以交給 agent 處理。不過講老實話，這些聽起來很夢幻的場景目前都還停留在想像階段，我還沒真的這樣用過。只要牽涉到個人帳號、登入狀態或金流操作，安全邊界跟人工確認機制（像是未來研究 auth-proxy 這類憑證隔離與簽核設計）都還得再仔細處理，這部分之後有空再來慢慢研究。

現階段我實際拿 openab-computer 在跑的，都還是公開資料的場景：請它去幾個電商平台查電腦零組件價格、做商品比價，或者找公開資料幫我整理成研究報告。這些事以前我自己也會開一堆分頁慢慢看，現在先把需求丟出去，過一陣子回來看結果就好。這差不多就是我目前把這套工具接進來使用的邊界。

後記
#

回頭看這半年，從最初想做一套集中式大後台「推廣給別人」，撞牆之後退回來打磨「自己慣用的工具」，最後慢慢拼湊出現在這套 agent 生態系，其實蠻真實的。

這兩件事做的時候我都覺得會派上用場，做到後來才體會到差別：一個是我在猜別人以後可能需要什麼，一個是我自己已經嫌麻煩好幾次，受不了才動手解決。如果你也想把 AI 變成自己的宇宙，我覺得真的不用一開始就想著蓋多宏大的平台，先從你這幾天每天都在嫌麻煩的那件小事開始做起，那個東西才會真正活下來。

最後順便留三個伏筆。最近在關注 OpenAB 生態系還有三個延伸專案，我目前都還沒實際動手串進來，先照它們官方 README 記一下各自想解決什麼問題，以後有空玩出心得再看要不要單獨寫成文章：

  1. openab-shepherd：解決「想讓外部 agent（像 Grok Bot）透過 MCP 在終端機裡啟動並操作 coding CLI，但又不想把安全規則交給 agent 自己決定」的問題——由 Shepherd 統一控管能開哪些程式、跑在哪裡、能拿到什麼憑證，以及權限確認怎麼回應。
  2. auth-proxy：解決「agent 需要呼叫外部 API 或服務，但又不想讓 agent 本身直接握有真實金鑰或憑證」的問題——讓 agent 只拿得到代理憑證，真正對外送出請求時才由 proxy 換上真實憑證，把敏感資訊隔離開來。
  3. nearpush（oab-nearpush）：解決「在電腦上跑 coding agent 時，不想一直盯著終端機看進度」的問題——把 agent 目前的狀態（例如正在執行、輪到你處理、需要授權、已完成）即時推到桌邊的手機畫面上，讓你一眼就知道它現在卡在哪。

好啦，這半年折騰的記錄就先寫到這邊（老實說，這篇也是跟 AI 一起協作整理的 XD）。接下來就看自己什麼時候有空，再把上面那三個新玩具接進我的宇宙囉。
